## Experiments

1. Batch shared atomic metrics updates per connection batch, with publication before writes and pipelined metrics snapshots. Unpinned pipeline-128 median: baseline 1,034,168 RPS; candidate 1,013,335 (-2.0%). The initial pipeline-1 results overlapped a subsequent build and must not be used for performance claims.
2. Add cache-line-aligned shard locks and borrow redirect URLs while copying responses, avoiding per-request Arc clone/drop. Controlled run pins server to CPUs 0–1 and client to 2–3, with no concurrent builds.

| Controlled workload | Baseline median RPS | Candidate median RPS | Change |
| --- | ---: | ---: | ---: |
| Pipeline depth 128 | 951,012 | 986,427 | +3.72% |
| Pipeline depth 1 | 32,835 | 32,472 | -1.11% |

Pipeline-128 p99 batch latency: baseline 48.223–48.575 ms; candidate 48.095–48.287 ms. Pipeline-1 p99: baseline 1.523–3.099 ms; candidate 2.263–21.823 ms. All controlled runs passed, with zero dropped requests, transport errors, and redirect mismatches. Short runs and host variability do not establish a consistent improvement. These are loopback processing measurements, not public HTTPS capacity.

Rejected production edits were restored. Two new regression tests remain in tests/integration.rs. All 26 Rust tests pass on the restored implementation. Candidate also passed clippy and all 10 blackbox tests (including SIGKILL durability).

## Public redirect path

Three independent curl requests from the laptop, no redirect following:

- Direct https://45.196.196.251/rushort/0: 302, time to first byte 302.503 / 279.726 / 292.944 ms.
- https://whiteye.in/s/0: 302, time to first byte 5451.393 / 699.246 / 685.081 ms.

The website route performs an upstream fetch before returning the 302. The sample shows a substantially slower public wrapper path; it does not isolate cold-start, TLS, geographic routing, or server time. Investigate caching immutable code-to-URL mappings or serving the redirect domain directly through Caddy before investing in more Rust micro-optimizations.

The telemetry includes a continuous synthetic saturating load generated by rushort-traffic.service. It should not be interpreted as organic user traffic. Consider separating synthetic and public counters and running capacity tests on demand.
